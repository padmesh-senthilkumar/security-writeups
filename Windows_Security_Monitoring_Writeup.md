# Windows Security Monitoring & Persistence

**Hands-On Lab Writeup — Event IDs, Persistence Techniques & Detection**
**Prepared by:** Padmesh S
**Environment:** Windows 10 VM (VirtualBox, unattended install, D: drive)

## Overview

This writeup documents hands-on Windows security monitoring and persistence exercises performed in an isolated Windows 10 virtual machine. It covers two core areas: understanding and generating key Windows Security Event IDs (logon activity, account management, and PowerShell logging), and simulating the three most common attacker persistence techniques. All exercises were performed in a self-contained lab environment for educational purposes.

---

## Part 1: Windows Event Viewer & Security Event IDs

Windows centralizes security-relevant activity in the Event Viewer, accessible via Start → search "Event Viewer". The Security log under **Windows Logs** records authentication events, account changes, and privilege use — the Windows equivalent of `journalctl -u ssh` on Linux. Events are identified by numeric IDs, which security analysts filter for during investigations and incident response.

### Key Security Event IDs Reference

| Event ID | Description | Security Relevance |
|----------|-------------|-------------------|
| **4624** | An account was successfully logged on | Successful authentication — normal baseline; suspicious if unexpected account, time, or logon type |
| **4625** | An account failed to log on | Failed authentication — clustered rapid failures from same source indicate brute-force |
| **4634** | An account was logged off | Session end — useful for tracking session duration |
| **4720** | A user account was created | New account creation — legitimate on onboarding; critical red flag if unexpected or after hours |
| **4732** | A member was added to a security-enabled local group | Privilege escalation — especially if adding to Administrators group shortly after account creation |

---

### Exercise 1: Generating and Reading Logon Events (4624 / 4625)

**Path:** Event Viewer → Windows Logs → Security → Filter Current Log → enter Event ID → OK

**Successful logon (4624):**
- Keywords: `Audit Success`
- Account Name: `WIN10LAB$` — a system/computer account logon during boot (`$` suffix = machine account, not a real user)
- **Logon Type** field: identifies HOW the logon occurred (interactive, network, RDP, service) — critical for spotting suspicious remote access

**Failed logon (4625)** — generated by locking the VM and entering the wrong password:
- Keywords: `Audit Failure`
- Same structural fields as 4624, with a **Failure Reason / Sub Status** field explaining WHY it failed (wrong password, locked account, etc.)

> **Detection principle:** Multiple 4625 events for the same account within seconds from the same source = brute-force signature. Same pattern as Linux SSH brute-force detection with fail2ban — Windows just structures it as fielded records instead of plain-text log lines.

### Exercise 2: Account Creation and Privilege Escalation (4720 / 4732)

Simulated a common post-compromise attacker pattern: create a backdoor account, then escalate it to admin.

**Step 1 — Create account (generates Event 4720):**

```cmd
net user backdoor P@ssw0rd123 /add
```

**Step 2 — Escalate to Administrators (generates Event 4732):**

```cmd
net localgroup Administrators backdoor /add
```

**4720 event:** `A user account was created` — Subject field shows `WIN10LAB\admin` (who acted, not the new account).

**4732 event:** `A member was added to a security-enabled local group` — also performed by admin.

> **Detection signal:** These two events occurred ~4 minutes apart for the same new account. A brand-new account escalated to admin within minutes of creation is a textbook attacker pattern — legitimate onboarding rarely moves this fast or grants full admin immediately. Time-proximity between 4720 and 4732 for the same account is itself a red flag.

**Key principle:** The **Subject field** tells you WHO acted. If that account is itself suspicious (newly created, unexpected), that's your investigation lead.

**Cleanup:**
```cmd
net user backdoor /delete
```

## Part 2: PowerShell Script Block Logging

PowerShell is both a powerful admin tool and one of the most commonly abused attack vectors — built into every Windows machine, trusted by default, and capable of nearly anything. Default Windows logging only captures that PowerShell was *opened*, not what was actually run. Script Block Logging addresses this gap.

### Default PowerShell Events (Low Investigative Value)

**Location:** Applications and Services Logs → Microsoft → Windows → PowerShell → Operational

| Event ID | Description |
|----------|-------------|
| 40961 | PowerShell console is starting up |
| 40962 | PowerShell console is ready for user input |
| 53504 | Engine/provider startup detail (background noise) |

These events only confirm PowerShell was *used* — they do not show what was typed or run. They fire identically whether the user is a legitimate admin or an attacker. Low value for investigation on their own.

---

### Enabling Script Block Logging (Event ID 4104)

Script Block Logging captures the actual code executed — not just "PowerShell opened." Not enabled by default — a common audit finding in real assessments.

**Enable via PowerShell (run as Administrator):**

```powershell
New-Item -Path "HKLM:\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Force

Set-ItemProperty -Path "HKLM:\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" -Name "EnableScriptBlockLogging" -Value 1
```

**Verify:**

```powershell
Get-ItemProperty -Path "HKLM:\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging"
```

Confirmed output: `EnableScriptBlockLogging : 1`

---

### Generating and Reviewing a 4104 Event

Ran a command commonly abused by attackers:

```powershell
Invoke-Expression "Get-Process"
```

`Invoke-Expression` is flagged by security tools because it executes whatever string is passed to it — commonly used to run obfuscated or remotely downloaded payloads. Legitimate uses exist, but it is a high-signal indicator in logs.

**Result:** `4104` Warning-level events appeared in the PowerShell Operational log, each containing the actual command text that was executed.

> **Key distinction:** "Script Block" does not mean a blocked script — it is a PowerShell term for a unit of code. This is a pure visibility/recording feature, like a camera, not a prevention control. The command runs identically whether logging is on or off.

## Part 3: Windows Persistence Techniques

After gaining initial access, attackers establish persistence to survive reboots, logouts, and password resets. The following three techniques use legitimate Windows features, making them harder to detect than obvious malware drops. All three were simulated in the lab, detected, and cleaned up.

### Persistence Techniques Summary

| Technique | Trigger | Privilege Needed | Detection | Cleanup |
|-----------|---------|-----------------|-----------|---------|
| Scheduled Task | Logon / boot / schedule | Admin | Event ID 106, Autoruns | `schtasks /delete` |
| Registry Run Key | User logon | None (HKCU) / Admin (HKLM) | Autoruns, `reg query` | `Remove-ItemProperty` |
| Malicious Service | Boot (no login needed) | Admin | Autoruns, `sc query` | `sc.exe delete` |

---

### Technique 1: Scheduled Task

Scheduled Tasks run code automatically on a defined trigger — at logon, at boot, or on a schedule. Attackers choose innocent-sounding task names to blend in with legitimate Windows maintenance tasks.

**Command used:**

```cmd
schtasks /create /tn "SystemUpdateCheck" /tr "calc.exe" /sc ONLOGON /ru SYSTEM
```

| Flag | Meaning |
|------|---------|
| `/tn SystemUpdateCheck` | Task name — chosen to appear legitimate |
| `/tr calc.exe` | The action; in a real attack this would be a malicious binary or script |
| `/sc ONLOGON` | Trigger: runs every time any user logs on |
| `/ru SYSTEM` | Runs as SYSTEM account — maximum privilege, no active user session required |

**Detection:** Event Viewer → Applications and Services Logs → Microsoft → Windows → TaskScheduler → Operational → **Event ID 106** ("User registered Task Scheduler task")

Event 106 showed: User `SYSTEM` (SID `S-1-5-18`), task path `\systemupdate\check`. `S-1-5-18` is the well-known, fixed identifier for the SYSTEM account on every Windows machine — worth recognizing on sight.

> **Key investigative principle:** Never trust the task name — the attacker controls it entirely. Always verify the actual binary path (`/tr` field). A suspicious name with a legitimate signed binary is fine; a normal-sounding name running an unsigned or unexpected binary is your red flag.

**Cleanup:**
```cmd
schtasks /delete /tn "SystemUpdateCheck" /f
```

---

### Technique 2: Registry Run Keys

Registry Run keys tell Windows to automatically launch a program at user logon. Two locations with different privilege requirements:

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run   # Current user only — no admin required
HKLM\Software\Microsoft\Windows\CurrentVersion\Run   # All users — requires admin
```

`HKLM` is higher value for an attacker — it fires for every user, regardless of which account logs in.

**Command used (HKCU — current user):**

```powershell
New-ItemProperty -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run" -Name "SystemHelper" -Value "calc.exe" -PropertyType String -Force
```

**Verify entry exists:**

```powershell
Get-ItemProperty -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
```

Confirmed output: `SystemHelper : calc.exe` sitting alongside legitimate entries (`OneDrive`, `MicrosoftEdgeAutoLaunch`).

**Detection:** **Autoruns** (Sysinternals) — free tool, no install needed. Shows ALL auto-run entries across Run keys, Scheduled Tasks, Services, startup folder, and more in one view. Legitimate entries show verified publisher signatures; malicious entries typically have no publisher and a vague or short binary path.

> **Key distinction:** Run keys require a user to log in to trigger. This makes them less powerful than Services for persistence.

**Cleanup:**
```powershell
Remove-ItemProperty -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run" -Name "SystemHelper"
```

---

### Technique 3: Malicious Windows Service

A Windows service runs as a background process, starting at boot without any user login required. This makes services the most powerful persistence mechanism of the three — an attacker can maintain access even on a machine nobody actively uses, running as SYSTEM.

**Command used:**

```powershell
New-Service -Name "WindowsHealthSvc" -BinaryPathName "C:\Windows\System32\calc.exe" -DisplayName "Windows Health Service" -StartupType Automatic
```

Result: `Status: Stopped, Name: WindowsHealthSvc` — registered and set to Automatic (auto-starts at next reboot).

**Why Services are more dangerous than Run keys:**
- Trigger at boot — no user login needed
- Run as SYSTEM by default — maximum privilege
- Harder for regular users to notice or accidentally remove
- Real malware (ransomware, RATs, backdoors) frequently installs itself as a service for exactly these reasons

**Detection:** Autoruns → Services tab, or `sc.exe query` to list all services and verify binary paths against expected legitimate values.

**Cleanup:**
```cmd
sc.exe delete WindowsHealthSvc
```

## Conclusion

Across these exercises, two consistent themes emerged. First, Windows generates rich, detailed security telemetry — but only if the right logging is enabled and monitored. Script Block Logging is disabled by default, and many organizations miss it entirely, leaving a blind spot that attackers actively exploit. Second, all three persistence techniques rely on legitimate Windows features: Task Scheduler, the registry, and the service control manager. This "living off the land" approach makes malicious activity harder to distinguish from normal administration — which is exactly why behavioral analysis (unexpected timing, unusual binary paths, unverified publishers, tight event-time proximity) matters more than simple keyword matching.

> **The key investigative principle across all findings:** Never trust labels. Task names, service display names, registry entry names, and account names are all attacker-controlled. The ground truth is always the actual binary being executed, the publisher signing it, and the timing and context of when changes were made.
